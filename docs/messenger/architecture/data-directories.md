# Папки данных и несколько аккаунтов

[Маршрутизация чтения](../../README.md) · [Хранилище](storage.md) · [Shutdown](shutdown.md)

Каждая папка данных — независимые `messenger.db`, профили подключения, история,
настройки и резервные копии. Это локальные рабочие пространства, не сетевые аккаунты.
Без параметров используется прежняя стандартная папка; существующие данные не
переносятся и не копируются. Новая папка начинает с пустого хранилища.

Приоритет: `--data-dir <путь>` → `MESHCORE_DATA_DIR` → стандартная папка ОС.
Относительные пути считаются от текущей рабочей папки процесса и нормализуются
в абсолютные. `~` само приложение **не разворачивает**; используйте абсолютный путь
или `$HOME` в shell. Пустая переменная окружения игнорируется; отсутствующий/пустой
аргумент и повторный `--data-dir` — ошибка. Выбора через UI и «последней папки» нет.
Для нестандартной папки её имя отображается в заголовке окна.

## Запуск

macOS, установленный app bundle (имя/путь приложения уточнить по месту установки):

```sh
open -n -a MeshCoreMessenger --args --data-dir "$HOME/Library/Application Support/MeshCoreMessenger-Work"
open -n -a MeshCoreMessenger --args --data-dir "$HOME/Library/Application Support/MeshCoreMessenger-Personal"
```

`-n` нужен, чтобы macOS запустила новый процесс вместо активации существующего.
При запуске из репозитория, в отдельных терминалах после Release build:

```sh
dotnet src/MeshCoreMessenger.Desktop/bin/Release/net10.0/MeshCoreMessenger.Desktop.dll --data-dir /tmp/MeshCoreMessenger-Work
dotnet src/MeshCoreMessenger.Desktop/bin/Release/net10.0/MeshCoreMessenger.Desktop.dll --data-dir /tmp/MeshCoreMessenger-Personal
```

Альтернативно задать `MESHCORE_DATA_DIR` в окружении процесса. Папка создаётся при
старте; файл вместо папки или невозможность создания/записи дают понятную диагностику
в stderr и код `3`. Вторая блокировка той же папки даёт код `2`, до открытия БД/UI.
Блокировка удерживается до окончания штатного shutdown и закрытия хранилища;
постоянный lock-файл не мешает следующему запуску после освобождения handle.

**Разные папки не разрешают совместное использование serial-порта:** два экземпляра
не должны подключаться к одной USB-ноде одновременно. Для параллельных соединений
нужны разные порты/ноды; для проверки окон достаточно offline-режима.

## Проверки реализации

Детерминированные Desktop-тесты проверяют приоритет источников, нормализацию,
неразворачивание `~`, фабрику путей, заголовок, одновременные блокировки разных
каталогов и отказ второй блокировки той же (включая эквивалентный путь).
Startup-тесты проверяют код `3` для файла и недоступного каталога; тест Unix permissions
проверяет read-only каталог даже при ранее созданном writable lock-файле.
Release build: 0 предупреждений/ошибок. Регрессии: Desktop 132/132, Core 127/127,
MeshCoreSharp 92/92; `git diff --check` и локальные ссылки документации проверены.

Ручная UI-приёмка: открыть два окна с разными папками, проверить заголовки и
независимость настроек; запуск с занятой папкой должен отказать без нового окна.
После штатного закрытия эта папка должна открываться снова. Без параметров должны
открываться прежние данные. Пользователь подтвердил успешную ручную проверку
02.10.2026 («все ОК»); агент самостоятельно визуальную проверку не выполнял.

## Debug: тестовые данные для визуальной разработки

Из корня репозитория перейти в Desktop-проект и выбрать **отдельную новую папку**:

```sh
cd src/MeshCoreMessenger.Desktop
dotnet run -c Debug -- --data-dir /tmp/mc-fake --seed-fake-data
```

`--seed-fake-data` работает только в Debug и только с явным `--data-dir`.
`MESHCORE_DATA_DIR` без аргумента не подходит; стандартная папка запрещена, включая
её символические alias. В Release флаг игнорируется с диагностикой, далее идёт
обычный startup. `--large` дополнительно создаёт канал со 100 000 сообщений
(для него выбрать другую пустую папку, например `/tmp/mc-fake-large`). Без seed-флага
`--large` ничего не делает.

После instance lock, **до открытия/миграций** существующей БД, выполняется read-only
проверка отсутствия нод, сообщений, контактов и профилей. На непустой БД, при повторе
seed или невозможности доказать пустоту — отказ с кодом `5`, без seed-записей/UI.
Символическая ссылка вместо файла БД запрещена. После открытия пустота повторно
проверяется через Core stores. Все fixture-записи выполняются через реальные
хранилища Core; прямой SQL используется только для read-only preflight.

Набор: одна fixture-нода, пять публичных каналов (пустой, 20 сообщений, 5000,
30 с 10 непрочитанными, длинное имя), пять личных контактов и шесть устройств
типов 2/3/4. Всего 5113 входящих сообщений; с `--large` — 105113. Есть многострочный
и длинный текст, строка без пробелов, URL, кириллица/emoji, даты сегодня/вчера/двух
прошлых месяцев. Устройства имеют разные даты advert, координаты `0,0` или заданные,
PresentOnNode true/false. Fixture-нода сохранена как выбранная offline-история.

В БД есть **один профиль-заглушка `[ТЕСТ] Fixture — не подключать`**: существующие
Core stores требуют session, а session требует профиль. Его Serial-путь — уникальный
несуществующий путь в fixture-папке, не путь реального устройства; AutoConnect=false,
Reconnect=false, DTR/RTS выключены. Профиль не выбирается автоматически seeder-ом.
Session сразу штатно завершается через `EndAsync` с причиной `FixtureCompleted`,
ещё до записи справочника/сообщений и запуска UI. Не создаются Companion-клиент,
transport или connection attempt. Проверено также отсутствие автоподключения после
явного выбора заглушки и сохранение завершённой session после reopen/startup.

Ограничения без изменения Core: исходящие сообщения и статусы доставки не создаются;
отдельного sender-name поля в доступной message projection нет (в каналах имя лишь
часть тестового текста). Для отсутствующих координат API snapshot не принимает `null`,
поэтому используется `0,0`. Все сообщения синтетические, длинные тексты намеренно
выходят за эфирные лимиты и не предназначены для отправки. Заполнение не является
одной общей транзакцией: при сбое остаётся частичная fixture-БД; автоматического
повтора/перезаписи нет, для нового заполнения выбрать другую папку.

UI2 показывает fixture-историю в ChatsView на публичной/приватной вкладках; fixture-нода
записана также как последняя подключённая для offline startup, без подключения к радио.
Для уже подготовленной `tmp/mc-fake` запускать из корня **без seed**:

```sh
dotnet src/MeshCoreMessenger.Desktop/bin/Debug/net10.0/MeshCoreMessenger.Desktop.dll --data-dir tmp/mc-fake
```

Ручная проверка ещё требуется: offline-окно с fixture-данными; стандартная и другие
папки не изменены. [Чек-лист чата](../plan/ui2-chat.md). После закрытия
повторить с seed (отказ), затем без seed (обычный offline-запуск сохранённой fixture-БД).

Автоматические проверки: Debug/Release build без предупреждений; Desktop 149/149
в обеих конфигурациях (включая 100 000 сообщений), Core 127/127 и MeshCoreSharp 92/92
в Release. Проверены нулевые connection attempts, reopen/startup завершённой session,
защита стандартной папки/символических ссылок и read-only отказ без изменений БД.
