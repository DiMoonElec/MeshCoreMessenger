# Управление контактами — отложенные мысли

05.10.2026. По запросу пользователя предложения сохранены для обсуждения позже.
Это не утверждённый план реализации D8–D10 и не поручение начать кодирование.
Приоритет сейчас — завершить первую итерацию для чтения/отправки сообщений.

## Предложения пользователя

- В shell добавить «Инструменты» над «Подключение». Универсальный компонент:
  список инструментов слева, представление выбранного справа, возможность
  регистрации новых инструментов. По виду похож на двухпанельный чат.
- Первый инструмент — добавление контакта: тип (чат, ретранслятор, сервер комнаты,
  датчик), имя, полный публичный ключ, кнопка добавления в ноду и БД.
- Если справочник ноды заполнен, предложить сохранить только в БД.
- В строках списка приватных чатов и устройств добавить меню «три точки».
  Контактные действия должны быть доступны для обоих типов списков; имеющееся
  меню приватной переписки также может использовать общие обработчики.
- Два уровня удаления: только с ноды, либо полностью с ноды и из БД.
  Для сохранённого локально контакта — возвращение в ноду.
- Полный ключ уже отображается; новый отдельный UI для него не требуется.
- При коллизии адресата показать короткое уведомление рядом со счётчиком байтов,
  а подробности — в модальной карточке со списком конфликтующих контактов.
  Проверять только контакты, присутствующие в справочнике выбранной ноды.
- Отдельный список кандидатов из adverts для ручного добавления сейчас не требуется.
  UI удаления, добавления и коллизий ещё предстоит согласовать.

## Что установлено в проекте

1. Приватные чаты и устройства — проекции локально известных Contacts, а не
   отдельный поток новых кандидатов NEW_ADVERT. CompanionSession уже публикует
   типизированные adverts; ReceiveCoordinator пока не создаёт список кандидатов.
2. Разделение локального контакта и присутствия на ноде уже существует:
   `Contacts.PresentOnNode`, identity `(NodeId, PublicKey)`. Полный snapshot
   помечает отсутствующие контакты false, но сохраняет записи и историю.
   Directory reader показывает оба состояния; устройства имеют «Сохранено локально».
   Сохранение отсутствующего контакта с перепиской покрыто тестами.
3. Readiness и session gateway уже запрещают отправку при коллизии шестибайтового
   префикса, проверяя только PresentOnNode=true, включая служебные типы контактов.
   В composer уже есть причина «Неоднозначный префикс ключа адресата».
4. Library и session leases имеют AddOrUpdateContactAsync, RemoveContactAsync,
   GetContactAsync. Нужны application workflows, persistence API и UI wiring,
   а не повторная реализация протокола.
5. Для базового local-only/present состояния не нужна отдельная таблица контактов
   или обязательная миграция. Нужны локальное создание/изменение и точечный commit
   подтверждённого результата. ApplySnapshotAsync нельзя использовать как
   обновление одного контакта: остальные будут помечены отсутствующими.

## Решения, которые потребуются при возвращении

- Один контакт с двумя состояниями присутствия; «результат не проверен» — отдельное
  состояние операции. Offline presence отражает последний подтверждённый snapshot.
  Все действия scoped по NodeId/полному ключу, не по имени или префиксу.
- Tools workspace имеет собственные ViewModel/представления и реестр инструментов;
  chat history/composer/receive machinery туда не переносить. Сохранение введённой
  формы при смене инструмента и narrow navigation согласовать отдельно.
- Для нового контакта: validate 32-byte key/тип/имя (31 UTF-8 байт), фабрика остальных
  полей, начальный flood. Дубликат ключа не должен молча переписывать существующие
  поля. Предложение при TABLE_FULL отделить от timeout/непроверенного результата.
- Возвращение контакта: сохранить identity/историю, рекомендуемый начальный flood;
  использование прежнего маршрута требует отдельного решения.
- Удаление только с ноды сохраняет переписку, draft и аналитику. Полное удаление:
  определить состав удаляемого, включая историю, draft, delivery analytics и UI
  preferences. Conversations → Contacts имеет ON DELETE RESTRICT; простой DELETE
  Contacts при существующей переписке не подходит.
- Нода и SQLite не имеют общей транзакции. Command → readback → local commit;
  после сбоя локальной записи повторять сохранение/проверку, а не слепо mutation.
  Не заменять весь справочник пустым после частичного readback. Полное удаление
  offline и обработку частичных результатов согласовать отдельно.
- Общий operation guard должен учитывать активные и queued доставки, pending
  writes и drafts, чтобы поздняя запись не восстановила удалённую переписку.
- Общие contact actions для строк чата/устройства и меню переписки; target
  захватывается до await, selection/node switch не меняют адресата операции.
- Неактивная кнопка Send не получает click: для подробностей коллизии предлагается
  кликабельное уведомление; business API при попытке отправки возвращает список
  конфликтов. Точный UI ещё не выбран.
- Полное удаление не является запретом будущего обнаружения/добавления: при новом
  появлении контакта на ноде следующая синхронизация может создать запись снова.

Предварительная сложность: shell/tools и формы — невысокая/средняя; локальные
контакты и node mutations — средняя; полное удаление с частичными результатами
и lifecycle — наиболее сложная часть. Разделять UI preview, local writes,
node workflows и полное удаление на самостоятельные подэтапы.
