# Простой поиск и каталог регионов: архитектура и план

Дата: 17.10.2026. Статус: **план, реализация и приёмка не выполнены**.
Основание: согласованный с пользователем сценарий одной карточки поиска.
Этот документ заменяет прежние решения REGION26–30 только в части карточки
поиска/каталога. Настройки default ноды и региона канала не перерабатываются.

[План REGION](stage-region.md) · [Wire](../../library/protocol/regions.md) ·
[Владение состоянием](../architecture/ownership.md) ·
[Node-scoped UI](../architecture/node-scoped-ui.md)

## 1. Требуемый результат

Карточка содержит только «Поиск регионов», «Отмена», неопределённую полосу
прогресса и список. Строка: имя региона, справа `+` или `−`.
Никаких списков репитеров, RSSI, ключей, маршрутов, флажков разрешений,
форм импорта, переименования, архивирования и технических итогов в этой карточке.
Ошибки передаются существующему механизму немодальных уведомлений.

При открытии показывается каталог текущей ноды. Поиск дополняет список;
автоматического добавления найденных имён в каталог нет. `+` сохраняет,
`−` удаляет из каталога, но строка остаётся с `+` до ухода из карточки.
Повторный поиск в рамках одного открытия не очищает результаты. После ухода
несохранённые строки забываются; повторное открытие читает каталог заново.

Список является объединением каталога и временных кандидатов текущего открытия.
Историческая таблица наблюдений не является источником восстановления списка.
Каталог доступен offline; поиск доступен только для текущей Online-сессии ноды.

## 2. Что уже есть и что требует изменения

| Компонент | Проверенное состояние | Решение |
| --- | --- | --- |
| MeshCoreClient.DiscoverRepeaterNeighborsAsync | Запрашивает full32, собирает отдельные push по tag, возвращает итог по deadline | Сохранить wire/API; 30 секунд задаёт Core-сценарий |
| MeshCoreClient.RequestRegionsAsync | Full key + reply path; исходящий путь берётся прошивкой из контакта | Сохранить; не переносить contact policy в библиотеку |
| MeshRequestCoordinator | Gate на весь remote exchange, matcher tag привязывается при MSG_SENT | Переиспользовать; проверить поздние ответы между попытками |
| RegionDiscoveryService | Scan/preflight/запросы, outcomes и observations; одна попытка, общий лимит 1 минута | Добавить явную политику поиска прямых соседей и bounded retries |
| RegionDiscoveryPreflight | Может объединять контакты и соседей; direct path разворачивается | Для нового режима только свежие zero-hop соседи, первые четыре; обратный путь всегда ZeroHop |
| RegionDiscoveryRouteWorkflow | Snapshot, владение контактом, mutation/readback, conditional restore | Расширить на существующий multi-hop direct contact; не обходить проверки версий |
| RegionService / SqliteRegionStore | CRUD, node scope, post-commit события, запрет удаления используемых записей | Переиспользовать, без новой миграции |
| RegionSettingsViewModel | Живёт вместе с MainWindow, объединяет default, каталог и поиск | Выделить состояние карточки и явный lifecycle её видимости |

Незакоммиченные изменения текущей рабочей копии (OnlyDiscoveredNeighbors,
30 секунд, четыре цели, автоматический consent и промежуточный список репитеров)
являются незавершённой основой, а не принятой реализацией этого плана.
Старые отчёты 425/425 и запуски с --no-build не подтверждают эти изменения.

## 3. Границы и контракты

### Библиотека

Остаётся одна MeshCoreSharp.dll. Здесь только Companion API, кодирование,
парсинг, RX, корреляция, транспортные/протокольные тайм-ауты. Не добавлять БД,
UI, автоматические RF retries или изменение контактов в RequestRegionsAsync.

Wire для соседа: поиск `37 80 04 tagLE32`, ответ `8E snr rssi path 92
inboundSnr tagLE32 publicKey32`. Запрос регионов: `39 publicKey32 01 00`;
сначала `06 route tagLE32 timeoutLE32`, затем `8C 00 tagLE32 clockLE32 CSV`.
ReplyPath задаёт исключительно обратный путь. Для direct zero-hop он пустой.
Discovery не возвращает имя репитера или полный маршрут. Полный ключ выбран
самим запросом (80; 81 запрашивал бы prefix8).

### Core

Использовать существующий IRegionService → IRegionDiscoveryService, не создавать
второй параллельный discovery pipeline. В RegionDiscoveryOptions выразить явную
политику DirectNeighbors; текущий bool можно заменить enum, если это делает
различие с прежним общим режимом понятнее. Старые explicit-target/general сценарии
не должны случайно менять поведение. Параметры простого режима централизовать
в Core (фабрика/именованный preset), а не разносить по ViewModel и workflow.

Core владеет выбором целей, подготовкой контактов, повторами, отменой, cleanup
и диагностикой. Desktop вызывает одну операцию с owner и CancellationToken.
Owner: NodeId, SessionId, Generation; все команды через SessionCommandGateway.
Порядок gates и непрерывный RX сохраняются.

Расширить progress DTO результатом завершённой цели: неизменяемый список
полученных имён и sources с RunId/owner. Это позволяет сохранить частичный
результат в UI до отмены/ошибки следующей цели. Callback только доставляет DTO,
не исполняет команды и не пишет БД. Итоговый result повторяет агрегат для
надёжного завершения; UI объединяет его идемпотентно.

Observations/outcomes остаются диагностикой Core с существующими retention и
source-key правилами. Автосохранение наблюдений не является добавлением в Regions.
Не раздувать схему: промежуточные timeout попыток логировать, терминальный outcome
цели сохранять один раз по существующему (run, target). При ошибке persistence
сохранить текущий контракт остановки, не выдавать её за отсутствие регионов.

### Desktop

Выделить RegionCatalogSearchViewModel (имя проектное) как дочерний компонент
RegionSettingsViewModel. Default-состояние, используемое заголовками каналов,
остаётся у существующего владельца. Новый компонент владеет только строками,
командами, lifetime открытия и отображением busy.

Строка хранит identity, имя, nullable сохранённый RegionId, определение для
повторного добавления и IsSaving. Значок выводится из подтверждённого состояния
БД, не переключается оптимистично. На время записи блокируется эта строка;
общий RF-поиск не обязан блокировать независимые операции каталога.

## 4. Алгоритм Core

1. Захватить актуального owner, запретить второй поиск этой операции.
2. Один scan full-key repeaters, CollectionWindow=30 секунд.
3. Отфильтровать Repeater, full32 и валидный path descriptor с нулём hops.
   Не добавлять известных контактов. Пустой список завершает операцию без
   чтения/подготовки контактов и без region requests.
4. Дедупликация по full key. Сортировка RSSI descending, SNR descending,
   затем full key ordinal. Выбрать максимум четыре ДО contact preflight.
5. Последовательно обработать каждую выбранную цель. Пятыми целями не заменять
   неответивших. Каждой цели задать reply path ZeroHop.
6. Для цели до трёх попыток, ответ до 15 секунд; между попытками 5 секунд.
   Задержки cancellable через TimeProvider. Корректный ответ, включая пустой,
   завершает цель. Повторять только timeout финального remote response после
   подтверждённого MSG_SENT. Не повторять timeout локального command exchange,
   uncertain send, malformed, unsupported, table-full, stale plan или transport error.
7. После terminal outcome выполнить cleanup, опубликовать имена и перейти
   к следующей цели. Ошибка отдельного репитера не стирает прочие результаты;
   session/storage failure останавливает весь run.

Удалить минутный deadline для этого режима: конечность задают scan, число целей,
попыток, задержки, существующие command timeouts и bounded cleanup. При сохранении
общего API deadline сделать его optional и отключить в simple preset. Не обещать
фиксированное время: только радио-окна до 30 + 4 × (3 × 15 + 2 × 5) = 250 секунд,
плюс локальные команды и cleanup. Поэтому прогресс неопределённый, без процентов.

### Подготовка контакта и восстановление

Для отсутствующего контакта разрешить firmware implicit addContact; после запроса
перечитать контакт и обновить DirectoryService, не удалять его автоматически.
Для существующего zero-hop контакта mutation не нужна. Для flood ИЛИ multi-hop
контакта временно установить zero-hop с подтверждением readback. Не использовать
старый многопереходный путь и не строить обратный путь разворотом.

Подготовку, цикл попыток и cleanup держать в одном владении контактом внутри
RegionDiscoveryRouteWorkflow (например, внутренний RequestWithRetryAsync).
Существующий одиночный RequestAsync делегирует общей реализации с одной попыткой.
Не повторять старый RegionDiscoveryPlan после того, как workflow уже изменил
или восстановил контакт: это нарушит revision/observation checks.
Перед каждой повторной передачей проверить сессию и что подготовленное состояние
контакта не изменилось. При конфликте завершить цель без следующей передачи.

После успеха/ошибки/отмены восстанавливать исходное состояние только при совпадении
подготовленного snapshot и observation version. Свежие advert/path изменения
сохранять. Cleanup использует отдельный bounded token и живую исходную сессию,
не новую reconnect-сессию. При disconnect ничего не переигрывать автоматически.

## 5. Каталог, идентичность и lifecycle карточки

Временный union хранится в памяти одного открытия. Identity соответствует
существующей паре node + полный region key; public key региона выводится штатным
RegionKeys из нормализованного публичного имени. Регистр не менять. Имена из разных
источников с одинаковой identity сливаются; одноимённые записи с разными ключами
не объединять. Сортировка имени ordinal со стабильным tie-break по identity.

При открытии читать GetRegionsAsync(includeArchived:true): архивные записи тоже
уже сохранены и показываются с `−`; удаление/добавление не заменять архивированием.
Это исключает невидимую сохранённую запись и конфликт при нажатии `+`.

Найденные `*`, private `$…` без ключа и некорректные публичные имена не добавлять
в UI-кандидаты. Уже сохранённые private/custom записи показывать. При удалении
сохранить их точное определение (включая ключ) только в памяти карточки, чтобы `+`
мог восстановить через существующий import/create service. Не выводить секреты
в observable текст, логи и сообщения. По уходе очистить ссылки на определения.

`−` вызывает DeleteAsync. При RegionInUseException сохранить `−` и уведомить
о назначении каналу; не менять назначения/default автоматически. `+` вызывает
CreatePublicAsync либо восстановление exact definition. RegionId после
повторного добавления может быть новым. Post-commit Changed обновляет membership
строк; поздний read не может откатить более свежую запись. При внешнем удалении
видимая строка также остаётся кандидатом до закрытия карточки.

MainWindow сохраняет RegionSettingsViewModel надолго, поэтому SetNode/Dispose
недостаточно для понятия «пока карточка перед глазами». Подключить явные
Activate/Deactivate к фактической навигации Settings и видимости карточки:
уход из Settings/закрытие содержащего раздела завершает открытие. Пересоздание
visual tree из-за layout/theme само по себе новым открытием не считается.

Контекст результатов: NodeId + session owner + card epoch + RunId. При уходе
отменить RF, очистить временный union, запретить поздние UI updates. Cleanup
дожидается существующий root task tracker; новое открытие не разрешает второй
поиск до завершения cleanup старого. Смена ноды аналогична закрытию/открытию.
Disconnect при остающейся карточке останавливает RF, но сохраняет уже видимые
результаты этой ноды. Shutdown ожидает задачи, не оставляет async void.

Состояния операции: Idle → Searching → (Cancelling) → CleaningUp → Idle.
Бегунок виден до конца cleanup, Search блокирован, Cancel после нажатия блокируется.
Кнопка отмены не очищает уже полученные регионы. Запись каталога, уже принятая
writer, завершается в старом NodeId; UI закрытой карточки результат не применяет.

## 6. Последовательность реализации

| Шаг | Изменения | Критерий завершения |
| --- | --- | --- |
| S1: политика целей | Options/preset, selection до preflight, только свежие zero-hop full keys, empty fast path | Тесты сортировки/четырёх/исключения старых контактов и multi-hop observations |
| S2: доставка и retries | RouteWorkflow для flood/multi-hop, общий owner на попытки, 15s/3/5s, progress результатов, отмена/cleanup | Проверены реальные командные последовательности через fake/loopback, поздний tag и restore conflicts |
| S3: состояние каталога | Дочерняя VM, union, membership post-commit, +/−, private exact restoration, card epoch | Временная SQLite: сохранение/удаление/повторное открытие/назначенный регион/смена ноды |
| S4: минимальная карточка | Кнопки, бегунок, строки; привязать реальный lifecycle Settings; удалить старый технический UI и мёртвые свойства | Проверка narrow/wide, клавиатуры, accessible names кнопок строк, отсутствия лишних элементов |
| S5: интеграционная приёмка | Собрать актуальные зависимости и тесты, проверить весь сценарий | Отчёт с фактическими counts, отдельная ручная/аппаратная проверка без подмены её mocks |

Не переписывать завершённые stages как будто новый UI существовал изначально.
Обновлять статус этого плана и отчёт проверки по факту. Режим commit/push будущей
реализации определяется новым заданием пользователя, не этим документом.

## 7. Проверки

- Fake clock: ответ discovery на 27-й секунде попадает в результат 30-секундного
  окна; 8-byte prefix, не-Repeater и multi-hop observation не становятся целями.
- Пять и более соседей, разный RSSI/SNR, дубликаты; запросы только первым четырём.
- Известный multi-hop и flood контакт временно zero-hop; ответный descriptor=00;
  существующий zero-hop не переписывается, implicit contact остаётся.
- Timeout final response → retry; пустой valid ответ → stop; immediate timeout,
  protocol error и session loss не вызывают повтор. Поздний tag не завершает
  другую попытку. Никаких параллельных remote requests.
- Отмена во время scan, wait, retry delay, preparation и cleanup; отсутствие
  новых SEND, сохранность частичных результатов, conditional restore.
- UI/SQLite: initial catalog, union без дублей, повторный scan, +/− и ошибки БД,
  RegionInUse, private delete/re-add с тем же ключом, архивная запись, post-commit
  гонки, закрытие/открытие, смена ноды и disconnect.
- Сборка должна включать актуальные изменённые зависимости; не принимать
  --no-build по старым binaries или ноль тестов за результат проверки.
- Hardware через CatCore только отдельным явно разрешённым запуском. Зафиксировать
  scan duration, число целей, попытки, полученные имена и подтверждение cleanup.
  Специализированный console-тест не включать в общий test runner.
