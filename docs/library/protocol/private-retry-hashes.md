# ЛС: attempt, хеш пакета и ACK

Исследовано 05.10.2026 по текущему upstream MeshCore. Это исследование кода,
а не аппаратная проверка всех вариантов прошивки. Повторы приложения пока
не реализованы; P1 добавил одноразовый API явных timestamp/attempt и планировщик.
План: [автоматические повторы ЛС](../../messenger/plan/d7-private-auto-retry.md).

## Хеш пакета

[Packet::calculatePacketHash](https://github.com/meshcore-dev/MeshCore/blob/main/src/Packet.cpp#L37-L45)
вычисляет усечённый SHA-256 от payload type и всего wire payload. Для обычного
ЛС маршрут, route type и path descriptor не входят в этот хеш. Исключение TRACE
не относится к текстовым сообщениям.

[Mesh::createDatagram](https://github.com/meshcore-dev/MeshCore/blob/main/src/Mesh.cpp#L452-L471)
создаёт payload ЛС:

```text
hash адресата | hash отправителя | MAC | ciphertext
```

[BaseChatMesh::composeMsgPacket](https://github.com/meshcore-dev/MeshCore/blob/main/src/helpers/BaseChatMesh.cpp#L382-L400)
подготавливает plaintext:

```text
attempt 0–3:   timestamp UInt32LE | flags=(attempt & 3) | UTF-8 text
attempt > 3:   timestamp UInt32LE | flags=(attempt & 3) | UTF-8 text | 00 | attempt UInt8
```

По [Utils.cpp](https://github.com/meshcore-dev/MeshCore/blob/main/src/Utils.cpp#L78-L132)
шифрование детерминировано, с нулевым padding; случайный nonce здесь не добавляется.
Изменение attempt меняет ciphertext/payload и, за исключением хеш-коллизии,
хеш пакета. Это относится и к 0 → 4: младшие два бита одинаковы, но дополнительный
полный номер отличается. Timestamp и текст могут сохраняться на протяжении цикла.

## Почему дословный повтор не заменяет новую попытку

[Mesh::onRecvPacket](https://github.com/meshcore-dev/MeshCore/blob/main/src/Mesh.cpp#L72-L182)
проверяет wasSeen перед ретрансляцией direct и перед обработкой TXT_MSG/FLOOD.
Пакет, хеш которого помнит узел, может быть отброшен как уже обработанный.
На получателе это происходит до расшифровки/обработки сообщения и формирования
нового ACK. Предположение пользователя о подавлении такого повтора ретрансляторами
подтверждается кодом. Только изменение пути/direct → flood при прежнем payload
не меняет хеш. Кеш конечен; поведение после вытеснения/перезапуска отличается.

Сетевые копии одной попытки должны подавляться. Новая попытка с другим attempt
должна проходить этот фильтр. Отсутствие дубликата в истории — отдельная задача
приложения получателя: firmware queueMessage передаёт текст и timestamp,
но не полный attempt. В нашем ingress сейчас уникален EventId, а не смысл сообщения.

## Хеш пакета и ExpectedAck — разные идентификаторы

По composeMsgPacket ExpectedAck — первые 4 байта SHA-256:

```text
timestamp | flags=(attempt & 3) | text | sender public key
```

Адресат и полный дополнительный attempt в этот digest не включены. Тег является
32-битным; значение из MSG_SENT авторитетно. Для одинаковых timestamp/text/sender:

| Attempt | Хеш пакета | ExpectedAck |
| --- | --- | --- |
| 0 | H0 | A0 |
| 1 | H1 | A1 |
| 2 | H2 | A2 |
| 3 | H3 | A3 |
| 4 | H4, отличается от H0 | A0, совпадает с attempt 0 |

A0–A3 обычно различаются; случайные 32-битные коллизии исключать нельзя.
Дополнительный attempt делает сетевой пакет уникальным, но ACK-теги циклически
повторяются через четыре значения. В текущем upstream при attempt > 3 максимальный
текст — MAX_TEXT_LEN − 2, то есть 158 UTF-8 байт при базовом лимите 160.

Получатель формирует радио-ACK с 4-байтным тегом, дополнительным attempt и случайным
байтом: это помогает различать сами ACK-пакеты. Однако
[MyMesh::processAck](https://github.com/meshcore-dev/MeshCore/blob/main/examples/companion_radio/MyMesh.cpp#L384-L398)
сопоставляет только первые 4 байта и сообщает Companion push:

```text
82 | ExpectedAck UInt32LE | RoundTripMilliseconds UInt32LE
```

Полный attempt в этом push отсутствует. Таблица ожидаемых ACK кольцевая;
при одинаковом теге RTT может считаться относительно более ранней записи.
Нельзя по одному такому push однозначно выбрать attempt 0 либо 4 или их маршруты.
Можно подтвердить одно логическое сообщение, если все совпадения принадлежат ему;
при совпадении между разными сообщениями подтверждение неоднозначно.

## Следствия для итоговой политики приложения

Уточнение пользователя 05.10.2026 заменило проект пяти попыток с одним timestamp:

- Исходный flood: T1/attempt 0, 1, 2.
- Исходный известный путь: T1/attempt 0, 1, 2, затем reset path,
  новое сетевое сообщение T2/attempt 0, 1 (T2 > T1). Всего пять, включая первую.
- Внутри фазы API также позволяет новый timestamp/attempt 0 на каждый повтор.
  Переход known → flood всегда начинает новую сетевую идентичность.
- Attempt 4 не используется: расширение и бюджет 158 байт для этой политики не
  нужны, лимит остаётся 160. Исследование 0/4 выше сохраняется как факт протокола.
- Детерминированного совпадения ACK 0/4 нет; 32-битные случайные коллизии остаются.
  Все теги T1/T2 хранить: поздний ACK T1 подтверждает тот же локальный MessageId.
- Новый timestamp делает сообщение новым для dedup адресата. Если он получил T1,
  но ACK потерялся, T2 может создать дубликат текста в его истории. Отправитель
  сохраняет один локальный пузырёк, но не может обеспечить exactly-once получателя.
- История аналитики различает маршрут/время каждой попытки и сетевую идентичность.
  При коллизии не назначает успех последней попытке по времени получения ACK.

Эта политика и API описаны в [итоговом плане](../../messenger/plan/d7-private-auto-retry.md);
API одиночного TX и планировщик реализованы в P1; исполнение цикла пока не подключено.
