# Эксперимент: канальный повтор с исходным timestamp

С 05.10.2026 эксперимент включён как «Повторить доставку» рядом с «Отправить как новое»; [актуальное поведение](channel-repeat-actions.md). Ниже сохранён отчёт исходного эксперимента.

Рабочий D7.1 с новым timestamp зафиксирован в `2a0919f`. По отдельному запросу
пользователя текущая экспериментальная версия изменяет «Повторить отправку»:
использует первый сохранённый ненулевой WireTimestamp этого сообщения. Новый
номер SendAttempt и статус сохраняются по-прежнему, но не меняют wire payload.
При reconnect/restart timestamp берётся из БД. Текст — прежний TransmissionText,
канал — с тем же fingerprint; черновик не участвует. Новые сообщения по-прежнему
получают новую временную метку. Для старой записи без WireTimestamp экспериментальный
повтор не может восстановить исходный пакет и завершается ошибкой без передачи.

## Что ещё влияет на одинаковость пакета

[BaseChatMesh.cpp](https://github.com/meshcore-dev/MeshCore/blob/main/src/helpers/BaseChatMesh.cpp)
формирует plaintext из timestamp, типа plain и `<имя отправителя>: <текст>`.
[Mesh.cpp](https://github.com/meshcore-dev/MeshCore/blob/main/src/Mesh.cpp)
добавляет hash канала и шифрует ключом канала.
[Utils.cpp](https://github.com/meshcore-dev/MeshCore/blob/main/src/Utils.cpp)
использует детерминированное AES-шифрование с нулевым padding и MAC; случайного
nonce для этого сообщения нет. При тех же данных и ключе payload должен совпадать.
[Packet.cpp](https://github.com/meshcore-dev/MeshCore/blob/main/src/Packet.cpp)
вычисляет хеш из payload type и payload. Маршрут/число хопов канального пакета
в этот хеш не входят. Имя добавляется прошивкой, а не приложением: не менять имя
собственной ноды и ключ канала между отправкой и повтором. Имя первой передачи
в локальной записи сообщения не сохранено, поэтому приложение не восстанавливает
его после изменения настроек ноды.

## Аппаратный эксперимент

1. Запустить обычный Desktop и подключить отправляющую и принимающую ноды.
2. Отправить уникальный текст в публичный чат; убедиться, что получатель его увидел.
3. Сразу выполнить «Повторить отправку» у этого же пузырька несколько раз,
   сохранив имя ноды и ключ канала.
4. Сопоставить число попыток в нашем UI, эфирный лог/хеш пакетов и число новых
   сообщений на приёмнике. Принятие команды нодой не доказывает повторный приём.
5. Для контроля отправить тот же текст через поле ввода как новое сообщение:
   новая временная метка должна дать другой пакет.

Ожидание по коду upstream: ноды, ещё помнящие хеш, отфильтруют повтор. Нода,
которая не слышала первую передачу, может принять повтор; после вытеснения хеша
из конечного кеша или перезапуска поведение может отличаться. Это проверяется
на оборудовании, а не имитируется как доказанный результат в TCP fake server.

Автотесты Core/TCP проверяют одинаковые timestamps и сохранность текста, включая
повтор после reconnect и Unknown. Desktop проверяет прежнее меню/пузырёк/черновик.
Эксперимент зафиксирован отдельным коммитом по запросу пользователя для ручной проверки.

## Результат аппаратной проверки

05.10.2026 пользователь выполнил эксперимент: повтор доставки не создал дубликат,
отправка как нового создала второе сообщение. Сохранён [подробный отчёт с пятью raw-пакетами и проверенными хешами](channel-repeat-hardware-dedup.md). Прямые и ретранслированные копии имеют одинаковый хеш; новый payload получил другой хеш.
