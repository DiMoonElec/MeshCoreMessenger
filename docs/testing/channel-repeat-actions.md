# Два действия для исходящего сообщения публичного чата

Реализовано 05.10.2026 по запросу пользователя. Контекстное меню исходящего
канального текста содержит два действия без подтверждений:

| Действие | В эфире | В локальной истории |
| --- | --- | --- |
| Повторить доставку | Прежние TransmissionText и первый сохранённый WireTimestamp | Новый SendAttempt прежнего MessageId, один пузырёк |
| Отправить как новое | Прежний TransmissionText с новой временной меткой | Новый MessageId/LocalSequence, первая попытка, отдельный пузырёк |

Оба действия используют выбранное сообщение, сохраняют редактируемый черновик,
не запускают повторную обработку сохранённого текста. Перед TX проверяются
текущие session/generation, NodeId, fingerprint и binding канала, UTF-8 бюджет
с текущим именем ноды. Для копии сохраняются прежние OriginalText/TransmissionText,
новая session и текущий binding. Исходное сообщение и его попытки не изменяются.

Общий send single-flight и ConversationOperationGuard действуют на оба сценария;
во время операции обе команды отключены. Offline, другая собственная нода,
отсутствующий слот, Sending и shutdown запрещают выполнение. Входящие/бинарные
и legacy-записи без захваченной попытки эти действия не получают. Приватный
повтор остаётся отдельным незавершённым этапом; preview сохраняет прежний пункт.

Новая временная метка превышает все сохранённые канальные WireTimestamp текущей
собственной ноды и учитывает часы/allocator MessageService. Это предотвращает
повторное использование timestamp ранее созданной копии после пересоздания
сервиса, даже если часы не успели изменить секунду. Timestamp пишется в Sending
до вызова Companion API. Новая копия получает обычный статус AcceptedByNode,
Failed или Unknown; ошибка не меняет статус исходного пузырька.

## Предел гарантии дедупликации

«Повторить доставку» повторяет данные для восстановления идентичности пакета.
Имя отправителя и ключ канала должны оставаться прежними: имя добавляет прошивка,
оно не сохранено в исходящей записи. Если имя менялось после первой передачи,
совпадение timestamp/текста не гарантирует совпадение хеша.

Дедупликация происходит по хешу payload в конечном кеше прошивки. Получатель,
помнящий хеш, отфильтрует копию; после перезапуска/вытеснения хеша повтор может
приниматься снова. Companion OK подтверждает принятие команды собственной нодой,
а не факт доставки участникам. Исследование firmware и аппаратный сценарий:
[эксперимент с исходным timestamp](channel-repeat-dedup-experiment.md).

## Проверки

- Release solution: без ошибок и предупреждений. Core 273/273, Desktop 315/315.
  В первом параллельном прогоне прежний тест shutdown route read завершился
  Connection reset by peer в teardown TCP fake server; отдельный повтор полного
  набора Core прошёл. Код этого сценария не изменялся.
- Core: копия после reconnect, сохранность source/draft/TransmissionText,
  первая попытка с новой session; пересозданный allocator превышает timestamp
  предыдущей копии, выбранной от того же исходного сообщения.
- TCP эмулятор, OK/ERROR: начальная отправка → повтор доставки → отправка как новое;
  3 команды, timestamps `[T, T, Tnew]`, разные MessageId только у новой копии,
  попытки исходного сообщения `[1, 2]`, попытка копии `[1]`, draft сохранён.
- Desktop: обе команды, offline/busy/двойной клик, одна запись после повтора,
  две после отправки как новое, сохранность старой попытки и черновика.
- Native `--repeat-channel-only`: Light/Dark × 420/960, оба настоящих пункта меню,
  без confirmation windows; черновик сохранён, копия появляется отдельно.
- Обычный offline startup не обращается к UI dispatcher до запуска Avalonia.

05.10.2026 пользователь подтвердил аппаратную приёмку обоих действий:
[пакеты, SNR, хеши и поведение получателя](channel-repeat-hardware-dedup.md).
Повтор доставки не создал дубликат в штатном приложении получателя; отправка
как нового создала второе сообщение. Автоматические испытания используют
только loopback/fake supervisor и временную SQLite, не моделируют радиодедупликацию
как подтверждённую аппаратную гарантию.
