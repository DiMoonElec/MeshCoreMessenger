# Позднее подтверждение ЛС — 04.10.2026

Пользователь подтвердил ручную проверку перехода статуса 04.10.2026 с временным
тайм-аутом 1 мс. После проверки тестовая подмена удалена: используется тайм-аут
из профиля подключения; сохранённые настройки профилей не изменялись.

После тайм-аута ACK сохранённая попытка `Unconfirmed` может стать `Delivered`.
Обновляется существующее сообщение; новая передача, попытка или пузырёк не создаются.
Интерфейс получает обычное post-commit уведомление исходящей истории.

## Обработка

- `CompanionSession` копирует готовую typed `MessageAcknowledgement` из публичного
  `AckPacket` в очередь событий. SQL и работа UI не выполняются в RX callback.
- `ReceiveCoordinator` обрабатывает только push-копию ACK, передавая полную identity
  собственной ноды, immutable SessionId, tag, RTT и время получения durable writer.
- SQLite сопоставляет ACK с private attempt по `(NodeId, SessionId, ExpectedAck)`.
  Ровно одна запись в `Accepted` или `Unconfirmed` подтверждается атомарно.
  Совпадения с завершёнными попытками также участвуют в обнаружении коллизии;
  при неоднозначности не выбирается ни первая, ни последняя запись.
- Дубликат ACK не меняет уже сохранённый RTT. `Failed`, `Unknown` и публичные
  сообщения этим механизмом не переводятся в Delivered. Событие раньше StartedUtc
  не подтверждает попытку.
- ACK до Accepted commit временно удерживается writer, если в этой сессии есть
  `Sending`; повторная проверка выполняется после записей статуса. Буфер ограничен
  64 различными ключами, обычное окно firmware — 8 отправок. Это буфер гонки записи,
  а не дополнительный срок ожидания ACK. Уже зарегистрированная Unconfirmed attempt
  не имеет нового временного ограничения на подтверждение в той же сессии.
- ACK имеет приоритет над конкурирующим timeout write: CAS не понижает Delivered,
  delivery observer допускает уже подтверждённую конкретную попытку.
- Ошибка SQL удерживает ACK в очереди исходящих записей, приостанавливает команды
  через существующий механизм и допускает повтор записи БД без TX. Очередь в памяти;
  несохранённое подтверждение не гарантируется после аварийного завершения процесса.
- Очистка истории удаляет attempts; позднее подтверждение ничего не восстанавливает.
  Событие другой сессии не применяется к старой истории, в том числе после reconnect.
  Схема SQLite и публичный Companion API не меняются.

## Проверки

Solution Release: 0 предупреждений/ошибок. Core Release: **262/262**, включая
9 новых регрессий. Desktop Debug: **305/305**. `git diff --check` пройден.

Регрессии на временной SQLite: точная identity/tag, дубликат, RTT, сохранность после
повторного открытия, коллизия с Unconfirmed/Delivered/Unknown, ACK до Accepted,
ошибка записи после Accepted commit и её восстановление, конкурирующий timeout,
ошибка записи позднего ACK и её восстановление, RTT вне signed диапазона,
устаревшее событие и удалённая история.

TCP-эмуляция использует production client/session/supervisor: два разных адресата,
два тайм-аута, поздние ACK в обратном порядке, независимые статусы и RTT, отсутствие
повторного TX; отдельно подтверждение после очистки истории. Аппаратная нода не
использовалась.

Ручная приёмка: отправить ЛС, дождаться «Доставка не подтверждена», затем получить
задержанный ACK. Тот же пузырёк должен показать «Доставлено»; отправки заново нет.
