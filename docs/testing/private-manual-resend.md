# Ручная отправка недоставленного ЛС как нового сообщения

05.10.2026. Приватный чат → ПКМ исходящего недоставленного сообщения →
«Отправить еще раз». Подтверждение не требуется. Создаётся новый локальный
MessageId/LocalSequence с тем же OriginalText, затем запускается обычный полный
цикл PrivateDeliveryCoordinator по текущему контакту и маршруту. Начало нового
wire message — новый timestamp и attempt=0; дальнейшие попытки подчиняются
существующей политике 3 flood либо 3 known/reset/2 flood. Первый старый пузырёк
и его attempts не изменяются. Это не продолжение прежнего цикла.

Пункт виден для Unconfirmed/Failed, включая legacy attempt без cycle. Prepared,
Sending/Active, AwaitingAck, Delivered и Unknown его не показывают. Входящие,
binary и публичные сообщения не получают приватное действие. Публичная надпись
«Отправить как новое» сохранена. Offline, неактуальный адресат/нода, текущая
отправка composer и ручная операция блокируют выполнение. Проверки повторяются
при вызове; пара NodeId/SessionId/Generation и MessageId захватывается до await.
Переключение workspace не меняет адресата уже принятого действия.

Core: IMessageService.SendPrivateAsNewAsync принимает source MessageId и текущую
session ownership, читает исходный текст/полный ключ из БД и заново применяет
текущий text processor/options/160-byte validator, как при обычном вводе текста.
Повтор использует production PrivateDeliveryCoordinator; legacy конфигурация
MessageService без координатора не поддерживает новый API. Сами старые сообщения
без cycle можно отправлять через production API.

Общая QueuePrivateAsync принимает отдельный source ID. Этот путь не читает, не
flush и не очищает draft buffer/store; вводимое сейчас сообщение не меняется.
Новое admission использует прежние queue limits, contact guard, owned session,
durable Prepared/Sending, cancellation и persistence pause. Автоматического
продолжения при reconnect нет. Схема SQLite v6 не меняется.

PrepareOutgoingMessage.PrivateResendSourceId — optional guard для writer-транзакции,
не новая колонка БД. До INSERT проверяется, что исходник ещё существует, принадлежит
той же ноде/переписке/full contact key, является исходящим текстом с точным
OriginalText и имеет итог Unconfirmed/Failed без подтверждённой доставки.
Для legacy проверяется последняя attempt; для нового сообщения — итог cycle.
Поздний ACK до admission отвергает создание копии атомарно. Очистка до admission
также не может восстановить исходное сообщение или создать копию из удалённого.

Поздний ACK после admission может подтвердить старое сообщение; новое остаётся
отдельным и имеет свои timestamps/ACK candidates/историю доставок. Оно не удаляется
автоматически: это результат отдельного явного действия пользователя. Надпись
повтора у старого пузырька скрывается после Delivered. Получатель может увидеть
новое сообщение повторно, поскольку timestamp изменён; это ожидаемое поведение.

Viewport: сохраняются существующие правила истории. При чтении старого участка
или переключении workspace новый bubble доступен в актуальном конце переписки;
вытеснять читаемый участок принудительной прокруткой не требуется.

Проверено:

- Store: все состояния legacy источника, запрет новых copies для delivered/
  pending/unknown, отдельные ID/sequence, сохранение исходной attempt;
- writer guard: чужой kind/переписка, изменённый OriginalText, ACK перед prepare;
- TCP production: первый flood цикл исчерпал 3 попытки, ручная отправка по текущему
  direct начинает новый timestamp/attempt=0, получает ACK, оставляет старый итог;
- новый цикл имеет прежний budget, исходный текст и независимый ACK tag;
- сохранённый и ещё не сохранённый draft не очищаются и не flush;
- поздний ACK старого цикла не подтверждает новую attempt, два bubbles остаются;
- delivered source и stale session отклоняются без новых TX;
- Desktop real SQLite: точная надпись меню, видимость/доступность, новый bubble,
  double-click, переключение workspace, оба черновика, поздний ACK и отдельный
  статус нового сообщения; оба публичных действия проходят прежние проверки.

Ручная приёмка: дождаться красного ЛС, набрать следующий черновик, выбрать
«Отправить еще раз», убедиться в появлении новой отправки при прежнем черновике.
Проверить поздний ACK, offline, обе темы и новые записи в карточке контакта.
