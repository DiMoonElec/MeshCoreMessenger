# Ручное чтение очереди на Heltec V3 — 25.09.2026

Проверка выполнена через `/dev/cu.usbserial-0001` на ноде `RnD CatCore🐈`.
Клиент запускался с `AutoReceiveMessages=false`; после `APP_START` публичный
`DrainMessagesAsync` вручную читал очередь до `NO_MORE_MESSAGES`.

Ограничивающая обёртка транспорта разрешала только точные команды `APP_START` и
`SYNC_NEXT_MESSAGE`. Команды радиопередачи и изменения настроек были заблокированы.
Первые два запуска использовали DTR=false/RTS=false; успешный запуск с сообщениями —
исправленную пару DTR=true/RTS=true.

Выполнено три отдельных запуска:

| Запуск | Команды | Результат |
| --- | --- | --- |
| 09:44:32 МСК | `APP_START`, `SYNC_NEXT_MESSAGE` | `NO_MORE_MESSAGES`, получено 0 сообщений |
| 09:44:55 МСК | `APP_START`, `SYNC_NEXT_MESSAGE` | `NO_MORE_MESSAGES`, получено 0 сообщений |
| 09:56:27 МСК | `APP_START`, семь `SYNC_NEXT_MESSAGE` | 6 сообщений, затем `NO_MORE_MESSAGES` |

Первые два вызова успешно обработали пустую очередь. После исправления линий Serial
третий запуск получил четыре личных сообщения от префикса `DF73015A6BB9` и два
канальных сообщения из каналов 0 и 1. Текст не выводился: harness зарегистрировал
только тип, адрес/канал и размер UTF-8. Все шесть событий `MessageReceived` были
доставлены до успешного завершения ручного drain на `NO_MORE_MESSAGES`.

После этих запусков выяснилось, что использованная пара `DTR=false`, `RTS=false`
могла перезагружать ESP32 при открытии порта. Последующая проверка с безопасной
парой подтвердила непрерывный рост uptime; см. [отчёт](serial-no-reset-2026-09-25.md).
Поэтому отсутствие заранее накопленных сообщений в первых двух проходах не считается
ошибкой `DrainMessagesAsync`: они могли быть потеряны при сбросе ноды. Успешный третий
проход физически подтвердил выдачу непустой смешанной очереди.

Сразу после drain отдельная проверка uptime показала 708 и 712 секунд между двумя
подключениями. Перезагрузки во время чтения сообщений и последующей проверки не было.

Для воспроизводимой проверки нового сообщения добавлен отдельный live-режим: он
выполняет начальный drain, до 60 секунд ждёт `MESSAGES_WAITING`, а затем вызывает
ручной drain повторно.
Запуск требует отправки нового тестового сообщения во время активного подключения:

```bash
dotnet run --project tests/MeshCoreSharp.Tests -c Release -- --serial-message-drain-live-test /dev/cu.usbserial-0001
```
