# BLE: Heltec V4 / 1.16 — нет ответа на первую команду

**Обновление 16.10.2026:** пользователь сообщил, что эта V4 заработала после
перепрошивки на 1.17.0. V3 после перепрошивки на 1.17.0 также работает.
Это подтверждает работоспособность обеих моделей на проверенной версии и усиливает
гипотезу проблемы 1.16, но не устанавливает точный дефект в исходниках.
Отдельные ошибки первого подключения зарегистрированы в
[отложенном отчёте](ble-first-connection-bugs.md).

16.10.2026. **Вероятна несовместимость BLE прошивки этой V4 с Windows.
Исправление в приложении не найдено; точная причина на стороне ноды не доказана.**

## Окружение

- Нода: Heltec V4, firmware `v1.16.0-07a3ca9`, по данным пользователя.
  Имя `MeshCore-SMK Mesh01` и отключение смартфона пользователь подтвердил.
- Windows 11 Enterprise LTSC, build `26100`, Realtek Bluetooth Adapter,
  driver `1.1072.2312.2502`. PnP status OK.
- Нода находится в списке BLE, сопряжена, NUS service обнаружен.
- GATT connection/subscription проходят, согласованный ATT MTU — 176.
  Подтверждение pairing protection level в WinRT — 3 (EncryptionAndAuthentication).
- До диагностики закоммичен подготовленный пользователем план REGION:
  `9e1a408`. Реализация REGION не выполнялась.

Windows GATT success подтверждает завершение операции записи, но не обработку
команды Companion. Сбой воспроизводится двумя Windows-клиентами именно с этой V4;
контрольная V3 работает, смартфон с V4 тоже работает. Пользователь также припоминает
проблемы этой ноды с BLE в других приложениях для ПК; это дополнительное наблюдение
пользователя, без отдельной трассы или точных версий тех клиентов.

## Что установлено по системной трассе

В `v4-gatt.etl` записан ограниченный сеанс Microsoft-Windows-BTH-BTHPORT.
Трассировка завершена, активного диагностического сеанса не оставлено.

- HCI Encryption Change: status 0, encryption enabled 1.
- ATT MTU response — 176; уведомления включены записью CCCD `0100`,
  это же значение возвращено при чтении дескриптора.
- RX value handle — `0x002D`; TX value handle — `0x002A`;
  CCCD — `0x002B`. WinRT characteristic handles 44/41 относятся к объявлениям,
  их нельзя подставлять вместо value handles в разборе ATT.
- Дважды отправлен ATT Write Request `12 2D 00 16 03`:
  DEVICE_QUERY с версией протокола 3 записывается в правильную характеристику.
  В обоих случаях получен ATT Write Response `13` от сервера.
- ATT Handle Value Notification не получен. Повторное чтение TX возвращает
  прежний `83`, а не DeviceInfo.

Таким образом, проблема проявляется после успешной защищённой ATT-записи.
Гипотезы о слишком длинном APP_START, отсутствии подписки или простом отсутствии
шифрования не объясняют этот сеанс. Трасса Windows не показывает, вызван ли
`onWrite` в прошивке и где теряется ответ Companion.

Пробные изменения защиты характеристик, дополнительного чтения/задержки и короткого
имени приложения полностью убраны. Исходный sample пересобран без них, без warnings.
Неподтверждённых обходов в production-код не добавлено. Bleak установлен только
в локальный ignored diagnostic venv; зависимости приложения не менялись.

## Проверка исходников и вероятная причина

Пользователь удалил и заново создал в Windows сопряжение **только**
`MeshCore-SMK Mesh01`, со смартфоном, отключённым от ноды. Повторный probe не помог.
Согласно
[документации Microsoft](https://learn.microsoft.com/en-us/uwp/api/windows.devices.bluetooth.bluetoothcachemode),
системный кэш GATT инвалидируется при unpair; его сброс экспериментально не устранил
сбой. Агент самостоятельно bond/адаптер/прошивку не менял.
После этого пользователь подтвердил фактическую синхронизацию со смартфоном,
а не только установление BLE-соединения.

Проверка формата APP_START по
[исходнику 07a3ca9](https://github.com/meshcore-dev/MeshCore/blob/07a3ca9/examples/companion_radio/MyMesh.cpp)
и [ESP32 BLE](https://github.com/meshcore-dev/MeshCore/blob/07a3ca9/src/helpers/esp32/SerialBLEInterface.cpp)
не выявила несовместимости формата первой команды. Прошивка требует encrypted/MITM
доступа к значениям RX/TX; его явное включение экспериментально не устранило сбой.

В BLE-реализации 1.16 флаг `deviceConnected` устанавливается только при успешном
`onAuthenticationComplete`; `onConnect` его не устанавливает. `writeFrame`
отбрасывает ответ, если этот флаг false. Возможная причина — различие обработки
повторного защищённого соединения с сохранённым bond у Windows и смартфона:
ATT уже работает, но ожидаемый callback готовности не перевёл прошивку в нужное
состояние. **Это гипотеза по исходникам, не подтверждённый device-side диагноз.**
Для подтверждения нужны логи callback/очередей на ноде. В 1.18 также изменена
реализация входящей BLE-очереди; успешный тест V3 не отделяет влияние версии
прошивки от модели ESP32 и используемого SDK.

Практический вывод: наиболее вероятна несовместимость BLE стека этой прошивки/ноды
с Windows. Влияние конкретного Realtek-драйвера на эту пару устройств окончательно
не исключено. Без доказанного обхода менять transport-код, добавлять повторы команд
или увеличивать timeout оснований нет.

Следующая содержательная проверка, если пользователь решит продолжить: сравнить
эту же V4 с более новой штатной прошивкой либо другим Windows BLE-адаптером;
для точного исправления — получить логи прошивки. Это предложения для отдельного
шага: перепрошивка, смена драйвера и настроек адаптера не выполнялись.

Логи, скрипты и исходники для сравнения — ignored `artifacts/ble-v4/`.
Проверялись только локальные read-only команды; SYNC_NEXT_MESSAGE, RF send и запись
настроек не выполнялись. Пользовательская БД не открывалась и не редактировалась.
