# План API для простого мессенджера на MeshCoreSharp

Дата анализа: 25.09.2026. Оценено текущее рабочее дерево, включая ещё не закоммиченные изменения личной отправки. «Реализовано» означает наличие рабочего высокоуровневого API и соответствующей реализации; наличие команды в `CommandType` само по себе не считается реализацией.

## 1. Вывод и границы задачи

**На уже настроенном компаньоне простой мессенджер можно разрабатывать сейчас.** Библиотека умеет получать контакты и каналы, принимать канальные и личные сообщения, отправлять текст в канал и контакту, отслеживать ACK личной отправки. Подключение доступно через Serial/USB и TCP.

Для первой версии предполагается, что радиопараметры, имя ноды, каналы и необходимые контакты уже настроены. Под «общими чатами» здесь понимаются каналы MeshCore, например `Public` и `#test`. Работа с room-серверами — отдельная задача.

Есть два уровня готовности:

- **Общение с существующими контактами в существующих каналах:** основные библиотечные API готовы. Нужны приложение, корректная обработка состояний и комплексная проверка пользовательского сценария.
- **Самостоятельное управление кругом общения из мессенджера:** отсутствуют запись/очистка канала и добавление/обновление/удаление контакта. Без этих API часть настройки остаётся в штатном приложении.

Публичное управление чтением входящей очереди реализовано после первоначального анализа. Следующие функциональные пробелы — настройка каналов и управление контактами.

## 2. Минимальные сценарии и состояние API

| --- | --- | --- |
| Подключиться к компаньону | `SerialMeshCoreTransport`, `TcpMeshCoreTransport`, `ConnectAsync`, `StartAsync` | Реализовано |
| Узнать собственное имя и ключ | Результат `StartAsync`, `SelfInfo` | Реализовано |
| Показать соединение и ошибки | `State`, `IsConnected`, `IsStarted`, `ConnectionStateChanged`, `BackgroundError`, типизированные исключения | Реализовано |
| Отключиться и подключиться повторно по запросу пользователя | `DisconnectAsync`, `ConnectAsync`, `StartAsync`, `DisposeAsync` | Реализовано; автоматического reconnect нет |
| Получить список каналов | `GetChannelsAsync`, `GetChannelAsync`, `ChannelInfo` | Реализовано; список включает пустые слоты, UI фильтрует `IsEmpty` |
| Получить список собеседников | `GetContactsAsync`, `Contact` | Реализовано; список также содержит другие типы нод |
| Получить накопленные и новые сообщения | `MessageReceived`, автоматический `MessagePump` после `StartAsync` и по `MESSAGES_WAITING` | Реализовано |

| Написать в канал | `SendChannelTextAsync(channelIndex, text, ct)` | Реализовано; возвращает результат локального принятия команды |
| Написать контакту | `SendTextAsync(Contact, text, ct)` или перегрузка с полным публичным ключом | Реализовано; передача обычного текста |
| Показать подтверждение личной отправки | `TextMessageSendResult.Accepted`, отдельная задача `Delivery`, `MessageDeliveryResult` | Реализовано: `Confirmed`, `TimedOut`, `NotExpected`; отмена/разрыв завершают задачу отменой/ошибкой |
| Дать другим нодам обнаружить себя | `SendAdvertisementAsync(ZeroHop/Flood)` | Реализовано; одна отправка по запросу |
| Узнать об обнаруженном контакте | `AdvertisementReceived`, `AdvertisementInfo` | Реализовано; обнаружение не гарантирует сохранение контакта в компаньоне |
| Обновить очередь вручную / возобновить чтение после ошибки | `DrainMessagesAsync(CancellationToken)` | Реализовано; после тайм-аута требуется reconnect |
| Добавить или изменить канал из приложения | Высокоуровневого API записи канала нет | Требует реализации для самостоятельного управления чатами; этап B |
| Добавить нового собеседника из обнаруженных нод | Высокоуровневого API записи контакта нет | Требует реализации, если прошивка не сохранила контакт автоматически; этап C |
| Удалить контакт / освободить его место | Высокоуровневого API удаления нет | Требует реализации для управления контактами; этап C |

Минимальному интерфейсу общения достаточно первых операций до отслеживания `Delivery` включительно. Адверты расширяют сценарий до знакомства с новыми нодами. Запись каналов и контактов нужна при выходе за пределы заранее подготовленной конфигурации.

Перегрузка `SendTextAsync` с публичным ключом не добавляет адресата в таблицу контактов компаньона. Радиоподтверждения входящих личных сообщений обрабатывает прошивка; отдельный метод отправки ACK приложению не нужен.

Для старой прошивки без `DeviceInfo.MaxChannels` метод `GetChannelsAsync` выдаёт `NotSupportedException`; отдельные слоты можно читать через `GetChannelAsync`. Автоматическое определение всех возможностей прошивки пока не реализовано.

## 4. Ограничения, которые должен учитывать мессенджер

### Доставка и повторная отправка

Для личного сообщения UI должен различать локальное принятие (`MSG_SENT`), ожидание ACK и результат `Delivery`. `Confirmed` означает полученное подтверждение ноды, а не прочтение человеком. `TimedOut` означает отсутствие подтверждения в срок: сообщение могло дойти. `NotExpected` означает, что ACK не ожидается.

Для канала успешный `SendChannelTextAsync` означает локальный `OK`. Подтверждения доставки всем участникам и списка прочитавших этот API не предоставляет. Нельзя показывать такой результат как подтверждённую доставку собеседнику.

Отмена после записи команды и разрыв связи не отзывают передачу. Исход операции может остаться неизвестным даже при исключении до получения результата отправки. Повтор — явное действие пользователя; автоматическая повторная отправка всех незавершённых сообщений после reconnect в MVP не нужна. Токен `SendTextAsync` управляет также ожиданием `Delivery`.

### Собеседник и идентичность чата

Входящее личное сообщение содержит только 6 байт ключа. Приложению нужен индекс контактов по этому префиксу: один кандидат — известный собеседник; ни одного — неизвестный; несколько — неоднозначность. Нельзя выбирать первый контакт или склеивать диалоги по отображаемому имени. Отправка принимает полный ключ, но кодировщик передаёт его шестибайтовый префикс: известные коллизии следует выявлять до отправки.

`ChannelMessage.Text` сохраняет присланный прошивкой текст вместе с префиксом имени автора. Отдельного полного ключа автора в модели нет; разбиение строки по двоеточию не даёт надёжной идентификации. Для MVP допустимо показывать текст целиком.

Индекс канала — локальный слот компаньона. При смене ноды или перезаписи слота приложение должно учитывать конфигурацию канала, чтобы не объединить историю разных чатов. Модели CLI-ответов, room-постов и бинарных данных не следует безусловно отображать как обычную личную переписку.

### Приём, история и поток UI

Подписываться на `MessageReceived` нужно **до `StartAsync`**: сразу после старта читается накопленная очередь, ещё до завершения загрузки контактов и каналов. Приложение должно принять сообщение даже при пока неизвестном имени контакта/канала и разрешить его позднее.

События вызываются в фоновой очереди, а не в UI-потоке. Обработчик должен быстро передавать данные в очередь приложения; сохранение и обновление UI требуют собственной обработки ошибок и диспетчеризации. Очередь событий библиотеки сейчас не ограничена по размеру: длительная блокировка обработчиков задерживает события и накапливает память, хотя RX продолжает работать.

Чтение сообщения удаляет его из очереди прошивки до сохранения приложением. Библиотека не является хранилищем истории и не гарантирует доставку «ровно один раз» при сбоях. Новый API чтения очереди не сможет восстановить уже потерянный кадр. Исходящие сообщения приложение сохраняет самостоятельно, не рассчитывая на собственное эхо через `MessageReceived`.

## 5. Доработки библиотеки и порядок реализации

Имена новых методов ниже — **предложения**, этих методов пока нет. Перед реализацией новых команд нужно проверить их формат и ответы по целевой прошивке; перечисления команд недостаточно.

### Этап A — управляемое чтение входящей очереди

Статус: реализовано 25.09.2026.

`MessagePump` по-прежнему не выполняет бесконечные автоматические повторы, но приложение может явно запустить проход без ожидания нового `MESSAGES_WAITING`. Отдельный публичный статус «читает/простаивает» не добавлен: для MVP достаточно завершения возвращаемой задачи и существующего `BackgroundError`.

- [x] Добавлен `DrainMessagesAsync(CancellationToken)` — явный запрос прочитать оставшуюся очередь до `NO_MORE_MESSAGES`, используя тот же pump и dispatcher.
- [x] Параллельные ручные вызовы используют один проход; метод работает при `AutoReceiveMessages=false` и совместно с автоматическим режимом.
- [x] Отмена отдельного ожидающего не отменяет общий проход; disconnect отменяет оставшиеся ожидания.
- [x] Ошибка явного прохода возвращается вызывающему. После тайм-аута повтор блокируется до reconnect, поскольку поздний ответ нельзя безопасно сопоставить.
- [x] Документировано: успешное завершение означает достижение `NO_MORE_MESSAGES`, а не завершение обработчиков событий приложения.

Критерии готовности: ручное чтение без нового push; работа с отключённым автоприёмом; параллельные вызовы и уведомления без потери пробуждений; отмена и disconnect; сообщения и ACK во время других команд; поздние ответы после тайм-аута. Поскольку ответы не имеют ID запроса, отдельно определить безопасное восстановление после тайм-аута: при невозможности отделить старый ответ требовать явного переподключения, а не обещать прозрачный повтор. Не вводить бесконечный цикл автоматических повторов.

### Этап B — настройка каналов из мессенджера

Приоритет: необходим для добавления общих чатов без штатного приложения; для существующих каналов можно отложить.

- [x] Добавлен `SetChannelAsync(index, name, secret, ct)`: индекс слота, имя и готовый 16-байтовый ключ.
- [x] Добавлен `ClearChannelAsync(index, ct)`, записывающий пустое имя и нулевой ключ по правилам прошивки.
- [x] Проверяются точный размер ключа, корректный UTF-8/NUL и 31-байтовая граница сохраняемой C-строки; ответ обрабатывается как `OK/ERROR` обычным dispatcher.
- [x] Добавлены `ChannelSecrets.DeriveHashtag` и `SetHashtagChannelAsync`: первые 16 байт SHA-256 от точного UTF-8 имени вместе с `#`; регистр и пробелы значимы, приватность такой ключ не обеспечивает.

Критерии готовности: запись и последующее чтение дают ожидаемую конфигурацию; очистка освобождает слот; некорректные параметры отклоняются; ошибка, отмена и interleaving push не нарушают следующие команды. Канал после настройки участвует в обычной отправке/приёме. Ключи не попадают в текстовое представление и штатные логи.

### Этап C — добавление и обслуживание контактов

Приоритет: необходим для общения с новыми обнаруженными нодами при ручной политике добавления; для уже сохранённых контактов можно отложить.

- [ ] Добавить `AddOrUpdateContactAsync(...)` с отдельной моделью записи, содержащей поля, требуемые прошивкой. Нормальное добавление из `AdvertisementInfo.DiscoveredContact` не должно требовать ручной сборки байтов.
- [ ] Добавить `RemoveContactAsync(publicKey, ct)` для удаления контакта и освобождения места.
- [ ] Обрабатывать отказ прошивки, в том числе отсутствие места, как понятный результат/исключение. После ошибки приём и дальнейшие команды должны работать.
- [ ] Описать обновление локального списка после адверта или изменения контакта. На первом этапе достаточно повторного `GetContactsAsync`; отдельные события изменений — улучшение, а не условие MVP.

Критерии готовности: `NEW_ADVERT -> добавление -> контакт в GetContactsAsync -> личная отправка с Delivery`; обновление сохраняет ожидаемые поля, удаление подтверждается повторным чтением. Ошибочные размеры ключа/пути, отмена, ошибки прошивки и адверты во время операций покрыты тестами.

`GetContactByKeyAsync` удобен для точечного обновления, но полный `GetContactsAsync` уже позволяет обойтись без него. Импорт/экспорт/шаринг контактов нужны для дополнительных способов обмена адресами и могут идти отдельным следующим этапом.

### Этап D — небольшие улучшения после первого мессенджера

Все доработки остаются в одном библиотечном проекте. Пример/GUI может быть отдельным проектом со ссылкой на `MeshCoreSharp`; транспортные и протокольные детали не должны переезжать в UI.

## 6. Что реализуется в приложении

| Задача | Ответственность приложения |
| --- | --- |
| Список чатов и выбор адресата | Кеш контактов/каналов, обработка неизвестных префиксов, фильтрация типов контактов |
| История переписки | Локальное хранилище входящих/исходящих, локальные ID, время получения и статусы доставки |
| Новые сообщения и непрочитанное | Очередь обработки, счётчики, уведомления, обновление UI |
| Статусы отправки | Сохранение исходящего до вызова API, обновление после принятия/ACK/ошибки; различение «не подтверждено» и «не отправлено» |
| Повтор сообщения | Явное действие пользователя; учёт возможного дубликата |
| Восстановление соединения | Кнопка reconnect, новая инициализация, перечитка контактов/каналов; без автоматической переотправки текста |
| Дедупликация и порядок | Сохранение исходных времён, осторожная эвристика повторов: timestamp или ACK не являются глобальным ID сообщения |
| Настройки приложения | Выбранный порт/адрес, оформление, локальная история; канальные ключи не выводятся в логи |

Минимальная последовательность запуска:

1. Создать транспорт и клиент; подписаться на сообщения, состояние и ошибки.
2. Подготовить очередь приложения, способную принять сообщения до загрузки справочников.
3. Выполнить `ConnectAsync`, затем `StartAsync`.

## 8. Что не входит в минимальный набор

BLE нужен отдельно, если целевое приложение должно работать через Bluetooth; для USB/TCP MVP он не является зависимостью. Настройка радио/мощности, provisioning новой ноды, удалённый CLI, login/status/telemetry, room-серверы, трассировка, вложения, бинарная отправка и управление приватными ключами не нужны для поставленной задачи обычного текстового общения на настроенном компаньоне.

Автоматический reconnect, автоматические повторы передач, полноценный механизм миграции истории и публикация стабильного NuGet — самостоятельные задачи. Их отсутствие не означает отсутствие API базового общения.
